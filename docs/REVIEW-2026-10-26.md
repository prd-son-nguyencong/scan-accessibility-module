## 1. Executive summary

1. Verdict: **chưa production-ready**. Lõi scan chạy được, nhưng có đường "false green", mất dữ liệu ở fixer, và gate CI không chạy.
2. Scan thất bại (trang không tới được, WAF/404, W3C `non-document-error`, Lighthouse lỗi) vẫn ra "Compliant", exit 0 (CLI-1, RPT-2, SCN-1, SCN-12, SCN-17).
3. Verification gate của trusted-fix không verify: chỉ scan route `/`, `sourceTraceResolved` luôn true, 0 target vẫn pass (FIX-1, FIX-3, FIX-4).
4. Apply không atomic hoàn toàn: post-verify lỗi để file đã sửa, không rollback; crash không recovery (FIX-15, FIX-16, FIX-17, CIS-5).
5. Legacy `src/fixer` là mặc định của `--fix`: `--dry-run` vẫn ghi file, `git stash` giấu WIP, CORS `*` trên mọi interface (LEG-1, LEG-2, LEG-7, LEG-32). Nên deprecate.
6. Report HTML có XSS sink, build report all-or-nothing làm mất cả scan (RPT-1, RPT-6, TRC-7, RPT-10).
7. CI chưa từng chạy: workflow trỏ `ada-scan/`, không có job `pnpm test`; 30/1392 test đỏ (OPS-1, OPS-2, OPS-3, OPS-4, OPS-19).
8. Điểm mạnh: nhiều bug có repro rõ, fix phần lớn effort S; 1362/1392 test pass; thiết kế trusted-fix (CAS, journal, shadow verify) đúng hướng, chỉ thiếu nối dây.
9. Ước lượng: Wave 0 (vài giờ mỗi bundle) gỡ được hầu hết P0; Wave 1 (vài ngày) đưa gate về đáng tin.

Luồng làm việc: source PDK (Liquid) → `pnpm sync:push` xuất JSON → import vào Site Studio → có link preview `*.preview.sites.stg.paradox.ai` → QA → client duyệt → gắn domain.

Tool sinh ra để **tự động hóa bước QA** thay cho việc kiểm tay từng page: accessibility, HTML validity, page speed. Dev sửa lỗi bằng CIS hoặc IDE (Cursor, Claude Code).

Yêu cầu chủ dự án đã xác nhận:

| Yêu cầu | Giá trị |
|---|---|
| Số page mỗi site | 5-20 |
| Nguồn danh sách page | Dev truyền tay, hoặc đọc sitemap nếu có. Với local cần cách riêng (xem A.4) |
| Ngưỡng Lighthouse | Mobile >= 80, desktop >= 90 ("càng cao càng tốt") |
| IDE của dev | Cursor, Claude Code |
| Trace về source | Hiện chỉ Liquid. Cần hỗ trợ thêm React, Next, HTML thuần. **Vue/Nuxt và Stencil để sau** khi tool hoàn thiện |

Hệ quả cho thứ tự ưu tiên: chế độ **scan URL preview** là chế độ chính. Các finding "báo xanh giả" (CLI-1, RPT-2, SCN-1) là blocker số một. Handoff cho IDE là tính năng cốt lõi, không phải phụ.

## A.2 Format import của Paradox (đọc từ `SITE_EXPORT.json`)

| Khóa | Nội dung |
|---|---|
| `elements_data` (83 mục) | 50 `snippet`, 13 `page`, 12 `script`, 5 `style`, 2 `layout`, 1 `site` |
| `component_data` (23) | Widget Paradox (vd `jobs-search`), cấu hình là chuỗi JSON trong `attributes` |

Điểm quan trọng với việc scan và trace:

1. **Page chỉ là khung ghép.** `pages/index.html` chứa `<main>` cùng các tham chiếu `{{snippet:<uuid>}}`. HTML thật nằm trong snippet, bọc bởi `layout`. Studio render phía server nên output cuối là HTML đầy đủ.

Mỗi lần install lại ghi đè lock (+88/-9 dòng, đã đo). Install kéo theo `postinstall` của host (`pnpm link ../web-component-poc 2>/dev/null || true`), trong khi thư mục đó **không tồn tại** ở `<path>/web-component-poc` (pnpm in cảnh báo "Installing a dependency from a non-existent directory"; thư mục chỉ có dưới `workday/`).

Vòng lồng sâu chỉ thấy ở lần đầu khi cần cài thật các gói mới; tôi không dựng lại được trạng thái đó. Test: `test/build-instrumented-spawn.test.js` (5 test). Kiểm chứng đầu-cuối khi trạng thái pnpm lỗi thời: 0 dòng postinstall, lock không đổi, scan xong. Giới hạn: timeout chỉ kill tiến trình con trực tiếp.

## A.5 Đề xuất: chiến lược trace (chưa triển khai)

### A.5.1 Với Paradox/Liquid

Vấn đề: preview không còn comment mốc (NEW-3). Đề xuất dùng **bản build local làm bản đồ tham chiếu**:

1. Build local một lần (có mốc snippet), lập chỉ mục: mỗi phần tử có fingerprint (tag, class, text rút gọn, vị trí cấu trúc trong snippet) và nguồn `snippets/<tên>.html:dòng`.
2. Với violation từ preview, khớp phần tử với chỉ mục bằng fingerprint. Chỉ gán confidence "high" khi khớp **duy nhất**; nhiều khớp thì "ambiguous" kèm danh sách ứng viên; không khớp thì `untraceable` kèm lý do (vd widget Paradox, nội dung động).
3. Dùng `hash_value`/phiên bản trong `meta_data` của JSON export (nếu tương ứng với bản push) để kiểm tra bản local có khớp bản đã lên Studio. Chưa kiểm chứng `hash_value` dùng được cho việc này.
4. Phân loại riêng: phần tử thuộc widget Paradox (`data-react-component`, `component_data`) và page khóa là **platform-owned**, đánh dấu không sửa được ở source.

Rủi ro đã biết: nội dung Studio có thể khác bản local (sửa tay trên Studio, dữ liệu `{{data:...}}`), nên fingerprint phải chịu được sai khác nhỏ và báo mức tin cậy thật.

### A.5.2 Đa framework: kiến trúc adapter

Logic Liquid hiện gắn chặt trong 5 file `src/tracer/` và `src/utils/paths.js`. Đề xuất interface chung: mỗi adapter nhận phần tử DOM lỗi và trả `{file, line, column, confidence, reason}`.

| Framework | Cách trace | Trạng thái |
|---|---|---|
| Liquid | `partial-map` + marker + fingerprint (A.5.1) | Có sẵn, cần sửa TRC |
| HTML thuần | Parse source bằng bộ parse có vị trí dòng, khớp phần tử | Mới, ưu tiên cao |
| React / Next | Plugin build thêm `data-src="file:line"` (React 19 bỏ `__source` nên cần plugin tự thêm) | Mới, sau HTML thuần |
| Vue / Nuxt | Plugin biên dịch thêm `data-src` | **Hoãn** theo chủ dự án |
| Stencil | Cần transformer riêng hoặc source map | **Hoãn** theo chủ dự án |
| Mọi framework (dự phòng) | Source map + khớp selector/text/class | Confidence thấp, luôn gắn nhãn |

Nguyên tắc: ưu tiên attribute thêm lúc build (độ chính xác theo dòng); DOM sinh từ component trả về dòng của component, ghi chú rõ; không trace được thì báo `untraceable`, không im lặng; tự phát hiện framework qua `package.json` và file config. Cần fixture thật cho từng framework trước khi tuyên bố hỗ trợ.

**Cảnh báo:** đây là hạng mục lớn nhất, nên là một wave riêng. Chưa thử khả thi của bất kỳ adapter nào.
